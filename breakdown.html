R&D

Multi-view instrumentation with Scene Capture 2D

Unreal Engine 5 · Scene Capture 2D · render targets · UI compositing
Problem
A client wanted several live camera angles on screen at once. Every extra active camera is another full render pass: culling, shadows, post-process.
What I did
Rebuilt the system around Scene Capture 2D components writing to render targets, composited in UI. Decoupled capture cadence from game framerate, trimmed show flags (no shadows / post / fog), and matched capture resolution to actual on-screen size.
Result
~13 ms frame time with every view live, inside a 16.6 ms / 60 fps budget, 12 ms of it on the render thread.
Next
Instanced static meshes and merged materials on the secondary captures would cut draw call submission further.

R&D

Deterministic material regeneration

Blender · Python (bpy) · shader node graphs
Problem
The first version patched hand-built shaders by writing hardcoded values into them. It worked until it silently did not: too fragile and unpredictable to trust.
What I did
Stopped patching and started regenerating. Every batch rebuilds the material graph from zero, so the shader graph is a build artefact rather than a hand-maintained file.
Result
Same input, same output, every run. Deterministic by design, which is the difference between a script that works on your machine and a tool a studio can rely on.
Next
A node-graph golden-image test per material would catch regressions automatically.

R&D

Headless Blender automation as an artist tool

Blender · Python (bpy) · Windows .bat · Alembic · Unity export
Problem
Every new skin and model was imported into Blender by hand, materials reassigned, then re-rendered: half a day of work, twice a week, and more when the team shipped a lot.
What I did
A self-contained automation pipeline behind one .bat: IMPORT_ABC -> ASSIGN_MATERIAL -> IMPORT_TEXTURES -> RENDER (stills + sequence) -> shared folder. Runs on any networked PC with Blender installed. No licensing, no server, no build step.
Result
Half a day per batch became one double-click. Roughly 2 days a week returned to the team, in continuous production use for seven months, run by the artists without an engineer.
Next
A queue with per-machine locking would let several artists batch at once without colliding.

R&D

Animation validation tool for animators

Unity · C# (editor + runtime) · animation retargeting
Problem
Scale and transform errors in animation were invisible in the DCC and only surfaced after a developer round-trip, which put the fix days away from the person who could make it.
What I did
Animators drop clips into a folder, open a scene, and one click applies the animation to a test rig. Deliberately built to fit the animation team's existing workflow rather than forcing a change to it.
Result
Errors that previously surfaced after a developer round-trip are caught by the animator in seconds, on their own machine.
Next
A batch mode over a whole folder would turn it from a spot check into a gate.

R&D

Six-wheel vehicle dynamics on Chaos Vehicle

Unreal Engine 5 · Chaos Vehicle · Blender (rig) · 3ds Max
Problem
An arcade racer lives or dies on how the car feels, and the target was specific: heavy but fast, chaotic yet responsive. Six-wheel drive is a configuration the engine defaults do not cover, and the city was in constant redesign underneath the vehicle.
What I did
A complete dynamics model: mass distribution, torque curves, wheel friction, cornering stiffness and suspension spring rates, iterated against playtest feedback. Plus a custom 6-wheel rig in Blender for accurate per-wheel ground response, integrated into the engine's physics pipeline.
Result
Handling read correctly at speed and held its identity across repeated map redesigns rather than being re-derived each time.
Next
Telemetry-driven tuning passes instead of playtest-only iteration.

R&D

Procedural terrain: World Machine into engine

World Machine · Unreal Engine 5 · Megascans
Problem
Getting a landscape that reads as a real place at scale, without hand-sculpting every metre of it.
What I did
World Machine as the backbone, built by iteration: base shape, blended and extended into another, then one detail layer at a time (distortion, wind, waves) until it held up. Implemented as a landscape in engine and dressed with desert assets.
Result
Every step of the creation is traceable from raw heightfield to finished environment, and the method carried back into production work.
Next
A parameterised macro so a variant terrain is a slider change, not a re-author.

R&D

Designing to 2 MB of RAM and 1 MB of VRAM

Unity · SplashEdit · PSXSplash · Lua · original PS1 hardware
Problem
A fishing game on real 1994 hardware: 33 MHz, 2 MB system RAM, 1 MB VRAM. The toolchain compiles, packs VRAM and builds the disc image. What no toolchain decides for you is what fits.
What I did
Budgeted every scene to the hardware up front, choosing what each scene could afford rather than optimising after the fact, and treated the constraints as design input.
Result
A stable 40 fps on original hardware, shipped as a genuine PS1-compatible disc image.
Next
A per-scene VRAM ledger checked into the repo so the budget is visible before art lands.

Large-scale world streaming on a proprietary engine

Eugen Systems in-house engine · World Machine · modular kits
Problem

R&D

Making unusable CAD deliverable

ArchiCAD export · Blender · Unreal Engine 5 · Lumen · Megascans
Problem
The practice supplied the house as an ArchiCAD export with plans, site photographs and sun data. The export was unusable as delivered: broken geometry, no clean topology, no UVs, no materials.
What I did
Rebuilt it in Blender: retopologised, unwrapped, assigned materials, then brought it into Unreal Engine 5. Built the surrounding environment from the site photographs and set lighting from the practice's sun data.
Result
Delivered as three still renders. The building permit was filed with these images and granted.
Next
A repeatable CAD-cleanup checklist would shorten the rebuild on the next commission.
